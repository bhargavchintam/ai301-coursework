# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-consistent | The plan's stated cause (the sentence that says why the failure happens) read against every step, artifact and control run in the repro-evidence block | No step, artifact or control run in the repro evidence shows behaviour that the stated cause cannot explain. A control run counts as explained when the plan itself states how the cause produces that control's result. Fails when a control run shows the component the cause blames working correctly and the plan does not explain it, or when the cause requires a condition the repro evidence shows to be absent. | required |
| cause-claims-backed | Each statement in the plan that names a cause or a fix site, read against the repro artifacts and the thread highlights | Every cause or fix-site statement is one of: (a) shown by an artifact in the repro evidence, (b) stated in the issue body or by any commenter in the thread highlights and not contradicted by the repro evidence, (c) marked as unverified anywhere in the plan (words such as "not yet verified", "unknown", "may", "to be pinned", "I have not checked"), or (d) an inference that the plan ties to named repro steps or control runs, where no step or control run in the repro evidence contradicts it. Fails when one such statement has none of the four. | required |
| targets-cause | The change the plan describes, read against the cause the plan states and any cause a maintainer stated in the thread | The described change modifies the mechanism the diagnosis names. Fails when the change only documents the symptom, adds a workaround the user must apply, or catches or hides the failure (a recover, a try/except, a docs note) while the plan or the thread names a code cause that is left unchanged. | required |
| one-change | The list of things the plan says it will change | Every listed item is needed to make the issue's failure stop. Fails when any item is a version upgrade, a refactor or module split, a new abstraction, a new user-facing option, a migration to another library, or a CI matrix that the issue's failure does not require. | required |
| starting-point-named | The plan's files, areas and approach | The plan names at least one file, module or code path, AND at least one step describes a code change at that place. A named module whose exact function is marked as still to be found passes. Fails when no file, module or code path is named, or when every step is to investigate, profile, look into, figure out, or explore. | required |
| test-observable | The plan's test plan read against the repro evidence's steps and artifacts | The test plan names a command or step from the repro evidence AND the exact expected result after the change (a value, an exit code, a message, or a named absence). Fails when the expected result is only "works", "passes", "feels fast", "looks better", or "the suite passes" with no repro step named. | required |
| thread-followed | Thread highlights from an OWNER, MEMBER or COLLABORATOR that name a cause, a fix site, or a preferred direction, read against the plan | If a maintainer named a cause, fix site or direction, the plan either follows it or names it and gives a reason for differing. When the maintainer listed several options without preferring one, following any one of them passes. Fails when the plan is silent about a maintainer-stated cause or direction that it does not follow. Passes when the thread has no maintainer signal. | required |
| policy-followed | The repo-facts block's contribution policy line, read against the plan comment | If the policy requires disclosing AI assistance on issues or comments, the comment contains a sentence stating whether AI was used and how. Passes when the policy says nothing about AI or only sets conditions on pull requests. | required |
| not-in-scope-stated | The plan's scope statement | The plan contains an explicit statement of at least one thing it will not change. | preferred |
| open-prs-acknowledged | Thread highlights that name an open pull request on this issue, read against the plan comment | If the thread names an open PR, the comment names it and says how the plan relates to it. Passes when no PR is named in the thread. | preferred |
| no-deadline | The plan comment | The comment contains no date, day, or timeframe by which the fix or PR will be delivered. | preferred |

## Verdict rule

Accept (ready to post and build from) only if every required check passes. An `unclear` grade on a required check counts as a fail: a plan whose grounding cannot be verified from the package is not ready to build from. Preferred checks never change the verdict; they are reported so a passing plan can be tightened before posting.
