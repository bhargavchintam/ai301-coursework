# Rubric: is this pull request ready to submit?

Every check below reads one thing and decides one concern. A pass condition is written so that a second grader, holding the same package, gets the same grade: it names the part of the package to read, the fact that must be there, and the fact that fails it. Nothing here grades the length of the description, the number of commits, or the polish of the prose; the thing graded is the diff, the evidence, and the repo's stated asks.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-within-plan | Every hunk in the candidate diff, read against the plan's Scope sentence, its Not-in-scope line and its Files list, plus the plan's Deviations section and the PR description | No hunk changes something the plan's scope does not name. A hunk that adds a user-facing option, flag or setting, bumps a dependency, renames or restructures code, or edits a file outside the plan's Files list (tests for a named file count as inside, and so does a CHANGELOG, whatsnew or release-notes entry the repo-facts line asks for) is such a hunk, unless the plan's Deviations section or the PR description names that exact hunk as a departure and gives the reason. Fails on the first unnamed hunk. | required |
| plan-delivered | Each deliverable the plan's Scope names (each code change, each test, each docs page or CHANGELOG entry it lists), read against the diff's files and hunks, with the plan's deferral or Deviations notes and the PR description | Every named deliverable appears in the diff, or the plan's deferral note, its Deviations section, or the PR description says that deliverable was dropped or deferred and why. Fails when a named deliverable is absent from the diff and nothing says so. A deferral stated in the plan or the description is a pass, not a fail. | required |
| description-matches-diff | Every sentence in the PR description that says what the diff contains or omits ("no changes beyond", "exactly as planned", "CHANGELOG entry included", "docs now document", "implements the plan in full"), read against the diff's file list and hunks | No such sentence claims a change the diff lacks, and no such sentence denies a change the diff contains. Fails on the first sentence that does either. A description that makes no such claim passes. | required |
| repro-rerun-shown | The test-evidence section, read against the repro evidence block in the plan context (the command, input or steps the reproduction used) | The evidence pastes the output of the reproduction's own command, input or steps re-run on the branch. Fails when the evidence shows only a different input or path (a control run, a single-file case where the repro used two files, a GET where the repro was a POST, a different header), or describes testing without output ("tested locally", "works now", "colors work", "used it for a day"). | required |
| test-plan-covered | Each failure mode the plan's Test plan names as a repro (by number, by input, or by command) that the plan-context repro evidence also shows failing before the fix, read against the test-evidence section; the plan's other test-plan items read against the evidence's stated results | Every repro the test plan names that the repro evidence showed failing before has a run in the evidence with its output pasted, and that output is the expected result the plan states for it (the value, exit code, message, count, or absence). Fails on the first such repro with no pasted run, or whose run shows a result other than the plan's expected result. Two other kinds of test-plan item are covered by a stated result in the evidence and need no pasted output: a control (the unchanged path: the dashed form, the no-ampersand input, the valid tarball, the double-quoted twin), and a check of behavior the plan adds that the repro evidence never showed failing (a new warning, a new error message), because the repro runs are what show the bug fixed and the suite line covers the added behavior. | required |
| repo-checks-run | The test-evidence section and the PR description, read against the repo-facts block's test and check commands (cargo test, go test, pnpm test, make check, fmt and clippy) and the plan's test-plan suite line | The evidence or description names the repo's test suite or check command and states its outcome (a pass count, "passes", "clean", "green"). Fails when the diff touches a source or test file and no suite or check command is named at all, or when one is named with a failing outcome that the description does not explain. Passes without a suite line when the plan's test plan names no suite or check command and the diff touches no source or test file (a config, theme or docs file only), because a suite proves nothing about a change no test reads. | required |
| no-debris | The added lines of the diff (lines starting with `+`) | No added line is a debugging print or log left in (an `eprintln!("DEBUG`, `print("DBG`, `console.log` for tracing, a commented `// log::debug!`), a commented-out block of code or a commented-out earlier attempt, a function or variable kept only as unused or dead (`#[allow(dead_code)]`, `_unused_`, "keeping for reference"), or a TODO or XXX about the change itself. Fails on the first such line. | required |
| no-unrelated-hunks | Each hunk of the diff, read against the fix the plan's scope names | Every hunk contains at least one line that changes the behavior the plan names or its tests. Fails on the first pure-churn hunk: a hunk in which every `-` line reappears unchanged as a `+` line (a block re-printed with identical content), a hunk whose only differences are whitespace, line breaks or import ordering, or a hunk that edits a function the fix does not touch. A single line removed and re-added inside a hunk that also changes behavior is not churn. | required |
| commits-describe-change | The commit list | Every commit message names the change that commit makes. Fails on a message that is only "wip", "fix", "fmt", "cleanup", "misc cleanups", or "hopefully". | preferred |
| template-sections-filled | The repo-facts block's pull-requests line (the template's sections, checklist items and required entries), read against the PR description and the diff | If the repo states a PR template or required asks, every named section, checklist item or entry is present: each named section appears in the description with content about this change, a "closes #" or "fixes #" line appears where the template asks for one, a checklist appears where the template requires one, and a CHANGELOG or whatsnew entry appears in the diff where the template requires one for a bug fix. Fails on the first named ask that is absent. Passes when the repo-facts line says there is no template and names no required entry. | required |
| issue-named | The PR description | The description names the issue number the plan belongs to, as `#<number>`, `closes #<number>` or `fixes #<number>`. Fails when no issue number appears in the description. | required |
| ai-disclosure-present | The repo-facts block's contribution-policy line, read against the PR description | If the policy says AI use must be disclosed (in any form, or on pull requests), the description contains a sentence stating whether AI tools were used and to what extent. Fails when the policy requires disclosure and the description has no such sentence. Passes when the policy states no AI rule, or only governs issues and comments. | required |
| maintainer-direction-engaged | Thread highlights from an OWNER, MEMBER or COLLABORATOR that name a direction, a caveat or an open question about the fix, read against the PR description | If a maintainer line names a direction, caveat or open question, the description names it and says how the change answers it. Passes when the thread has no maintainer line of that kind. | preferred |

## Verdict rule

Accept (submit) only if every required check is `pass`. Any required `fail` gives `reject` (hold). An `unclear` grade on a required check counts as a fail and gives `reject`: a claim the package does not let the grader verify is not evidence. Preferred checks never change the verdict; they are reported so a passing PR can be tightened before it is opened. An honest shortfall is not a fail: a deliverable the plan or the description says was deferred, with the reason, passes `plan-delivered`, and the verdict turns only on what the diff, the evidence and the repo's asks show.
