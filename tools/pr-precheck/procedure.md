# Procedure: how this tool grades a PR package

The graded object is a pull request read against the plan it claims to implement. Three reads are side-by-side and decide most verdicts: the diff against the plan's scope, the evidence against the plan's test plan, and the description against both. The order below puts the plan in the reader's hands before the diff, and the test plan before the evidence, so the PR's own story never becomes the frame it is graded by.

## Read order

1. Read the repo-facts block first. Write down three facts: the "pull requests" line (template sections, checklist items, a required "closes #" line, a required CHANGELOG or whatsnew entry, or "no template"), the "contribution policy" line (does it require AI-use disclosure: yes, comments-only, or no), and every test or check command either line names.
2. Read the issue title and body. Write down the issue number and the failure in one line: the wrong behavior and its trigger.
3. Read the thread highlights. For each line whose author association is OWNER, MEMBER or COLLABORATOR, write down whether it names a direction, a caveat, or an open question about the fix. Ignore NONE authors for this list.
4. Read the plan context, all of it, before the diff. Write down, as separate lines: the repro evidence (the command, input or steps the reproduction used and what they showed before); the Scope sentence; the Not-in-scope line; the Files list; every deliverable the scope names (each code change, test, docs page or CHANGELOG entry); every deferral, known-limit or "leaves open" sentence; and the Test plan broken into items, one per repro, control and command, each with its expected result.
5. Only now read the diff. Write down the file list from the `+++ b/` headers, and for each `@@` hunk one line: the file, what it changes, and whether the plan's scope names it. Mark every `+` line that is a debug print, commented-out code, a dead or unused helper, or a TODO. Mark every pure-churn hunk: one where every `-` line reappears unchanged as a `+` line, one whose only differences are whitespace, line breaks or import ordering, or one that edits a function the fix does not touch. A hunk that also changes a behavior line is not marked.
6. Read the commit list. Write down each message and whether it names a change.
7. Read the test-evidence section. Write down each run it shows: the command or input, the pasted output, and the stated outcome of any suite or check command. Note any run that is described but not shown.
8. Read the PR title and description last. Write down: the issue number it names; every sentence that claims what the diff contains or omits; every sentence that names a deviation, deferral or shortfall; every template section heading or checklist it carries; any AI-use sentence; any sentence that names a maintainer's direction or question.

The plan sits before the diff because `diff-within-plan` and `plan-delivered` compare the diff to a boundary the reader must already hold; read the diff first and its hunks look like the plan. The test plan sits before the evidence for the same reason: `test-plan-covered` needs the list of expected runs before the shown runs can be ticked off. The description sits last because its claims are graded against the diff and the evidence, never the other way round.

In live mode the parts come from files and commands instead of sections: steps 1 and 3 read `.github/PULL_REQUEST_TEMPLATE.md`, `docs/CONTRIBUTING.md` and the issue thread (`gh issue view <number> --comments`); step 4 reads `plan.md` including its Deviations section, with the student's posted reproduction comment as the repro evidence; step 5 runs `git diff main...HEAD` in the working copy; step 6 runs `git log main..HEAD --oneline`; step 7 reads `test_evidence.md`; step 8 reads `pr_draft.md` (first line is the title, the rest is the description). Read nothing else in the working copy.

## Evidence gathering

For each check, the gathering move is fixed and uses the notes from the read order:

- `diff-within-plan`: take the step-5 hunk list and the step-4 Scope, Not-in-scope and Files lines. Next to each hunk write "named" (the scope or files list covers it, or it is a test for a named file), "departure named" (a Deviations note or a description sentence from step 8 names this exact hunk with a reason), or "unnamed". The first "unnamed" hunk is the evidence.
- `plan-delivered`: take the step-4 deliverable list. Next to each write the diff file or hunk that delivers it, or "deferred: <the plan or description sentence>", or "absent". The first "absent" is the evidence.
- `description-matches-diff`: take the step-8 fidelity claims. Next to each write the diff fact that confirms it or the diff fact that contradicts it (a claimed file not in the file list; a denied change present as a hunk). The first contradiction is the evidence.
- `repro-rerun-shown`: take the step-4 repro command or input and the step-7 runs. Record the run whose command or input is the reproduction's own, with its pasted output, or record "only <other path> shown" or "described, no output".
- `test-plan-covered`: take the step-4 test-plan items and split them into repros (failure modes named by number, input or command that the step-4 repro evidence shows failing before the fix) and stated-result items (controls on the unchanged path, and checks of behavior the plan adds that the repro evidence never showed failing). Next to each repro write the step-7 run that pastes its output and whether that output is the plan's expected result, or "no pasted run". Next to each stated-result item write the evidence sentence that states its result, or "not stated". The first repro with no pasted run or a mismatched result is the evidence; a stated-result item with a stated result is covered.
- `repo-checks-run`: take the step-1 check commands and the step-4 suite line. Record the step-7 or step-8 sentence that names a suite or check command with its outcome, or "none named". When none is named, also record whether the step-5 file list has any source or test file; a config-only or docs-only diff whose plan names no suite records "no suite applies".
- `no-debris`: take the step-5 marked `+` lines. Record the first one, quoted.
- `no-unrelated-hunks`: take the step-5 marked hunks. Record the first one: the file and what it changes without touching the fix.
- `commits-describe-change`: take the step-6 list. Record the first message that names no change.
- `template-sections-filled`: take the step-1 template asks. Next to each write the description heading, line or diff file that answers it, or "absent". The first "absent" is the evidence. With "no template" and no required entry, record "no template".
- `issue-named`: take the step-2 issue number. Record the description sentence that carries it, or "no issue number in the description".
- `ai-disclosure-present`: take the step-1 policy fact. If disclosure is required, record the step-8 AI-use sentence or "none". If the policy has no AI rule or governs only issues and comments, record "not required".
- `maintainer-direction-engaged`: take the step-3 list. For each direction, caveat or question, record the description sentence that names it, or "silent". With no maintainer line of that kind, record "no maintainer signal".

## Check execution

1. Execute the required checks in this order: `diff-within-plan`, `plan-delivered`, `description-matches-diff`, `repro-rerun-shown`, `test-plan-covered`, `repo-checks-run`, `no-debris`, `no-unrelated-hunks`, `template-sections-filled`, `issue-named`, `ai-disclosure-present`. Then the two preferred checks, `commits-describe-change` and `maintainer-direction-engaged`. Every check is executed and reported even after a required check has failed; the verdict is assembled at the end, not on the first fail.
2. For each check, apply the pass condition in `rubric.md` literally to the gathered record. Grade `pass` when the condition holds, `fail` when the record shows it does not hold, and `unclear` only when the package lacks the whole part the check reads (no diff section, no test-evidence section, no plan context at all). Missing content inside a part that exists is a `fail`, not an `unclear`: a test-evidence section that shows no run of the repro exists and fails `repro-rerun-shown`.
3. Each grade carries one line of evidence quoted or paraphrased from the package: the unnamed hunk, the absent deliverable, the contradicted claim, the repro run or its absence, the uncovered test-plan item, the suite line, the debris line, the churn hunk, the missing template ask, the issue number, the disclosure sentence or its absence. When a check passes, quote the fact that satisfied it; "looks fine" is not evidence.
4. A check is graded from the gathered record without re-reading the package. Re-read only when the record lacks the fact the check needs, then add the fact to the record so the next check does not repeat the search.
5. Never grade a check on the length, headings or polish of the description, or on the number of commits. A terse description whose claims match the diff passes `description-matches-diff`; a long one with a claim the diff contradicts fails it.
6. Do not skip a check because another check already failed on the same hunk or sentence. A commented-out block fails `no-debris` on its own; the same hunk can also fail `no-unrelated-hunks` if it reformats untouched code, and each is reported on its own evidence.
7. An honest shortfall is graded as the rubric says: a deliverable the plan or description defers with a reason passes `plan-delivered`, and a description that restates that deferral passes `description-matches-diff`.

## Verdict assembly

1. Apply the verdict rule from `rubric.md`: `accept` only if all eleven required checks are `pass`. Any required `fail` gives `reject`. Any required `unclear` is treated as `fail` and gives `reject`. Preferred checks never change the verdict.
2. The deciding check is the first required check in execution order that failed. In the summary, name it and quote its evidence line. When more than one required check failed, name the deciding check first and list the others after it, each with its evidence line. On an accept, state that all required checks passed and list any preferred check that failed so the author can tighten the PR before opening it.
3. In live mode, after the verdict, hold the title and description in `pr_draft.md` against `voice-guide.md` and quote any rule the draft breaks. This never changes the verdict.
4. Emit the fenced JSON block last, in the shape SKILL.md gives, with every check listed (required and preferred) in execution order, each with its grade and its one-line evidence, and the verdict. Nothing follows the JSON block.
