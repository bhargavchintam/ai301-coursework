# Evidence guide: where evidence lives in a PR package

This file is the map for the checks in `rubric.md`. `procedure.md` says when to gather each family; this file says where each family lives and what a pass looks like. The four headings are the harness's failure categories under the eval README's names: plan fidelity is silent-drift, test evidence is not-tested, diff quality is unreviewable, standards and comms is standards-wall. A PR that fails none of the four is a clear accept.

## Plan fidelity (harness category: silent-drift)

Checks that read here: `diff-within-plan`, `plan-delivered`, `description-matches-diff`.

Where it lives. In an eval bundle: the plan's boundary is in the "Plan context" block, in the sentences starting "Scope", "Not in scope", "Files" and "Test plan", plus any sentence marked "deferred", "known limit", "deviation" or "leaves open". What actually changed is the "Diff" section of the candidate PR: the `--- a/` and `+++ b/` file headers give the file list, and each `@@` hunk gives one change. The description's fidelity claims are the sentences in "Description" that say what the diff does or does not contain ("no changes beyond", "exactly as planned", "implements the plan in full", "CHANGELOG entry included"). In live mode: the Scope, Not in scope, Files and Test plan lines of `plan.md` and its dated "Deviations" section; the diff from `git diff main...HEAD` run in the working copy on the branch; the description part of `pr_draft.md`.

What good looks like. List the files the plan names, then list the files the diff touches; every diff file is in the plan's list or is a test for one, and every hunk changes the thing the scope sentence describes. A CHANGELOG, whatsnew or release-notes entry the repo asks for is inside the boundary even when the plan's Files line omits it. Silent drift in the "more" direction is a hunk the plan did not ask for: a new option, flag or setting (`--time-format`, `experimental.menuFollowsWindowTheme`, `resolve_symlinks`), a dependency bump in `go.mod` or `Cargo.toml`, a rename pass, a helper rewritten "while in there", and no Deviations note or description sentence naming it. Silent drift in the "less" direction is a deliverable the plan names (a docs page, a CHANGELOG entry, a second test, a second fix) that the diff does not contain while nothing says it was dropped. An honest deviation re-ties the mismatch: a dated note in the plan's Deviations section, or a sentence in the description, that names the exact departure and the reason ("`%VAR%` expansion is not handled here; its escaping rules differ, deferred per the plan"). A description claiming more than the diff delivers ("the docs now document the limitation" with no docs file in the diff) or less ("no changes beyond the fix" next to an unrelated refactor hunk) is silent drift, graded here and never as a comms problem.

## Test evidence (harness category: not-tested)

Checks that read here: `repro-rerun-shown`, `test-plan-covered`, `repo-checks-run`.

Where it lives. In an eval bundle: the proof is in the "Test evidence" section of the candidate PR, and sometimes also in a Before/After block inside the "Description". What it must be read against is in the "Plan context" block: the "Repro evidence" sentences (the command, input or steps the reproduction used, and what they showed before) and the "Test plan" sentence (each repro by number or name, each control, the suite or check command, and the expected result after). The repo's own check commands are on the repo-facts block's "pull requests" and "contribution policy" lines (cargo test, go test, pnpm test, cargo fmt, clippy, make check). In live mode: `test_evidence.md` captured from the branch (the repro script's before and after output, `make test-unit`, `make lint`, `black --check`, `make typecheck`), read against the test plan in `plan.md` and the student's posted reproduction comment on the issue.

What good looks like. Decisive evidence pastes the reproduction's own command or input re-run on the branch with the output under it, and that output is the expected-after the plan states: the printed lines and exit 0 where the plan says "expect the last lines printed and exit 0", `?997;1n` where the plan says `?997;1n`, a count of 0 escape sequences where the plan says none. Every repro the test plan names has a pasted run: when the plan names two failure modes, two runs appear with output. A control the plan names needs only its stated result ("the `-j 64` control unchanged", "still renders"), and so does a test-plan item that checks behavior the plan adds rather than a failure the repro evidence showed ("same-key redefine prints the one-time warning"), because the repro runs are what show the bug fixed and the suite line covers the added behavior. A second failure mode that the repro evidence showed failing (repro 2 in a two-repro report) is a repro, and a stated result does not cover it. A suite line is required whenever the diff touches a source or test file; a config-only or docs-only diff whose plan names no suite needs none. The suite or check command is named with its outcome ("`cargo test` passes", "511 tests", "fmt and clippy clean"). Not decisive: "tested locally, colors work now"; "verified working on my machine for a full day"; a run of the control path only (the single-file case when the repro was two files, a GET when the repro was a POST, a different header than the repro's); a second failure mode in the test plan with no run; a suite never named.

## Diff quality (harness category: unreviewable)

Checks that read here: `no-debris`, `no-unrelated-hunks`, `commits-describe-change`.

Where it lives. In an eval bundle: the "Diff" section (every `+` line and every hunk) and the "Commits" list of the candidate PR. In live mode: the diff from `git diff main...HEAD` and the branch's `git log main..HEAD --oneline`.

What good looks like. A reviewable diff shows the fix and its tests and nothing else: a reader can tie every hunk to the plan's scope sentence. Debris tells, each one a fail on its own: a debugging print or log left in (`eprintln!("DEBUG accept err`, `// eprintln!("help colors`, `// log::debug!(`), a commented-out block of code or a commented-out first attempt "kept for reference", a dead or unused helper (`#[allow(dead_code)] fn count_open_fds`, `fn _unused_buffer_probe`), a TODO about the change itself (`// TODO: ring buffer?`). Churn tells, each a pure-churn hunk with no behavior line in it: a block of lines removed and re-added with identical content, an import block reshuffled with nothing added that the fix needs, a struct literal reformatted in a function the fix never touches, a "fmt pass" commit whose hunks touch code outside the fix. One line removed and re-added inside a hunk that also changes behavior is not churn. Commit messages that name the change ("gate --help colors on stdout being a terminal") are the preferred shape; "wip", "fix", "fmt + cleanup", "misc cleanups while debugging" are reported but never decide the verdict on their own.

## Standards and comms (harness category: standards-wall)

Checks that read here: `template-sections-filled`, `issue-named`, `ai-disclosure-present`, `maintainer-direction-engaged`.

Where it lives. In an eval bundle: the repo's asks are on two lines of the "Repo facts" block: "pull requests" (the template's sections, its checklist, a required "closes #" line, a required CHANGELOG or whatsnew entry) and "contribution policy" (the AI-use rule, if any). Where the PR honors them is the "Description" of the candidate PR (section headings or labels such as "Description:", "User-facing changes:", "Problem:", "Solution:", "PR Checklist:", "Requirements:", the "closes #" or "fixes #" line, the AI-disclosure sentence) and, for a required entry file, the "Diff" file list. Maintainer direction is in "Thread highlights" on lines whose author association is OWNER, MEMBER or COLLABORATOR. In live mode: `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md` in the repo working copy, the title and description in `pr_draft.md`, and the issue thread read with `gh issue view <number> --comments` or `gh api`.

What good looks like. Compliant means every ask the repo states is answered with content about this change: "Motivation and Context: Closes #7648" where the template asks for Closes #; "Requirements: cheatsheets regenerated (no binding changes); code formatted; integration test added; new error text internationalised" where the template has a checklist; a CHANGELOG.md hunk in the diff where the guide asks for an entry; "Per the repo's AI policy: this change was AI-assisted with me reviewing and understanding every line" where the policy says AI use must be disclosed. A visibly ignored ask is a wall on its own, however good the fix: a required checklist with no checklist and no issue number, a strict all-AI-use-must-be-disclosed policy with a description that says nothing about AI use. When a maintainer asked a question or named a caveat on the thread, the description that names it and answers it ("On the thread's open question about name uniqueness (fdncred): this change keeps names non-unique on purpose") is the preferred shape. Whether the description's claims match the diff is plan fidelity, above, not a comms question.
