# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| maintainer-alive | Repo facts: the "last 5 default-branch commits" list (dates and author names), measured against the capture date (against today in live mode) | At least 1 of the 5 commits is dated within 90 days of the capture date AND is by a human, or is a bot merge of a human's pull request. A commit by a name ending in `[bot]` that merges a bot's own pull request (for example a dependabot branch) does not count. | required |
| repo-in-use | Repo facts: the "archived:" flag on the repo line and the "last push to any branch" date | archived is "no" AND the last push is within 180 days of the capture date | required |
| spec-present | The "opened by" line (author association), the issue body, and maintainer comments in the thread (author association OWNER, MEMBER or COLLABORATOR) | Passes if any one is true. (a) A maintainer (OWNER, MEMBER or COLLABORATOR) opened the issue, however short the body is. (b) For a bug: the body names the wrong behaviour and how to trigger it (steps, a snippet, an error message, or the file and line). (c) For a feature, enhancement or docs request: the body names the concrete changes to make AND the request has standing in the project, meaning the opener's association is CONTRIBUTOR, or a maintainer has replied in support or stated what to build. A feature request from a bot or from a user with association NONE, with no maintainer reply, fails even if it is well written, because whether to build it is still an undecided product question. Also fails when the thread has discussed the design for a long time without settling what to build. | required |
| scope-bounded | The issue title, body, labels and the full comment thread | The issue asks for one bounded change. Grade the size of the work asked for, not the length or polish of the write-up: a short maintainer-filed issue passes, and a trailing "etc." on a list of examples of the same small fix does not fail. Several edits that together make one change (for example one new docs page plus pointers to it from existing pages) count as one bounded change. It fails if it is an umbrella, tracking or "mega" issue meant to be split into separate pieces of work; if it is a usage or support question; if a maintainer says the fix needs changes to core internals; if the fix asks for performance, concurrency or architecture work (threads, multi-processing, changing an algorithm's complexity); or if the approach is still being debated in the thread and no maintainer has stated the accepted approach. | required |
| no-failed-attempts | Repo facts: the "linked PRs" list with each PR's state, plus the issue's "opened by ... on" date | Fails if 2 or more linked PRs are closed without merge, or if the issue was opened more than 3 years before the capture date and has at least 1 linked PR closed without merge. Otherwise passes. | required |
| unclaimed | Repo facts: "this issue: assignees" and "linked PRs", plus claim comments in the thread ("I'll take this", "/assign", "working on this", "opened PR #...") | assignees is "none" AND no linked or thread-mentioned PR is open or merged AND no claim comment was posted within 60 days before the capture date. A PR mentioned in the thread whose state is not shown counts as open. Closed unmerged PRs and claim comments older than 60 days with no follow-up do not block. In live mode on Path Review, apply the house rule in scope.md: classmates' claim comments do not block. | required |
| ai-policy-allows | Repo facts: the "contribution policy" line | Passes unless the policy states an outright ban on AI-generated or AI-assisted contributions (for example "we do not accept AI-generated code"). Conditions such as disclosure, understanding and testing every change, or human review pass. "Discouraged" passes. No CONTRIBUTING file or no statement passes. | required |
| maintainer-endorsed | The "opened by" line (author association), the issue labels, and the author association on each comment | At least one is true: the opener is OWNER, MEMBER, COLLABORATOR or CONTRIBUTOR; the issue carries a "good first issue" or "help wanted" label; a maintainer said in the thread that the change is wanted | preferred |
| responds-fast | Repo facts: "maintainer first-response sample" | At least 1 sampled issue opened within 180 days of the capture date got a maintainer reply in 7 days or less | preferred |
| ships-releases | Repo facts: "latest release" | A release is dated within 12 months of the capture date | preferred |

## Verdict rule

Accept only if every required check passes. An `unclear` grade on a required check counts as a fail, because a first issue I cannot verify is not one I should spend my limited hours on. Preferred checks never change the verdict. They only rank the issues that are accepted: more preferred passes ranks higher.
