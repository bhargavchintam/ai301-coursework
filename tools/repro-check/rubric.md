# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record (version of the software under test, operating system or platform, and how it was installed) read against the versions and platform the issue's body names. In live mode: the draft report against the issue thread | The report states the version of the software it ran and the OS or platform it ran on, AND those either match what the issue targets (same version line, same OS family) or the report says what differs. A report with no version or no OS fails. A version or OS that differs from the issue's without the difference being named fails. | required |
| steps-rerunnable | The repro report's steps and inputs: the commands run, the input files or snippets, the starting state. In live mode: the draft report | A stranger with the named environment could re-run the steps from a clean start using only what the report contains: every input file or snippet is shown, or is taken from the issue and the report says so, or is described precisely enough (the exact keys, values, offsets or lines) that a reader can build it from the report plus the issue; every command or UI action is written out, and nothing depends on data, configuration or a repository the reader cannot get (a private repo, an internal config, "my usual setup"). | required |
| behavior-shown | The report's artifacts (command output, log lines, error text, screenshot description) read against the failure the issue describes | When the report says the bug reproduced, at least one artifact shows the same failure the issue describes: the same error message, panic, wrong output or missing element. An artifact that shows a different error (a syntax error, a validation error, a compile error where the issue describes a runtime panic), a run that only shows setup, or no artifact at all fails. When the report says it could not reproduce, this check passes if an artifact shows the issue's trigger being run and the outcome observed. | required |
| honest-outcome | The report's conclusion sentences (words like "confirmed", "reproduced", "root cause", "cannot reproduce") read against the artifacts in the same report | The conclusion claims no more than the artifacts show. Passes when a reproduction claim is backed by an artifact of the issue's failure, or when a cannot-reproduce says so plainly and names what may have differed from the reporter's conditions. Fails when the report says "confirmed" or "reproduced" over an artifact that shows something else, states a root cause without showing evidence for it, or asserts reproduction ("100% reproducible", "guaranteed") with no artifact. | required |
| claim-specific | The candidate claim comment read against the issue's body and thread | The claim names something specific to this issue (the symptom, the version tested, a file or function from the issue, or the concrete next step) and promises only investigation, a report, or a proposed approach. Fails when the comment is a "+1", "same here", "any updates?", a request to be assigned with no plan, a promise of a fix by a date, or when it asserts a reproduction that the report does not back. | required |
| policy-respected | The repo-facts block's contribution policy line, read against both comments. In live mode: CONTRIBUTING.md and any AI policy file in the repo | If the policy requires disclosing AI assistance on issues or comments, at least one of the comments states whether AI was used and how. If the policy asks that comments be written in the contributor's own words, the comments are not boilerplate. Passes when the policy says nothing about AI, or only sets conditions on pull requests. | required |
| template-asks-met | The repo-facts block's bug-report template line, read against the report's environment record and steps | Each item the repo's bug template asks for (for example version, OS, install method, config, logs) that applies to a reproduction appears in the report. | preferred |
| control-run | The report's artifacts | The report includes a control run, a second run with one thing changed (a different version, no flag, English instead of Japanese) that shows the failure absent, so the trigger is isolated. | preferred |

## Verdict rule

Accept (ready to post) only if every required check passes. An `unclear` grade on a required check counts as a fail: proof I cannot verify from the package is not proof a maintainer can verify either. Preferred checks never change the verdict; they are noted so I can improve a package that already passes. In a claim-only draft (live mode before the report exists), only `claim-specific` and `policy-respected` decide the verdict, and the other checks are reported as not yet applicable.
